# درون‌ریزی رسانه و Lazy load — 4.0.0-rc.5

## تشخیص دقیق، نه حدس درباره سرور کاربر

پیام قبلی برای هر مقاله فقط false برمی‌گرداند و خطای اصلی sideload را حذف می‌کرد. بدون دسترسی به گزارش میزبان نمی‌توان گفت علت قطعی سایت کاربر permission، temp، بسته ناقص یا تداخل افزونه بوده است. این نسخه نقاط شکست بازتولیدشده و نقص گزارش خطا را اصلاح می‌کند:

1. `set_post_thumbnail` برای معتبر دانستن تصویر به HTML تولیدشده وابسته است؛ یک فیلتر تصویر/Lazy/offload می‌تواند آن را خالی کند. اکنون ابتدا فایل و MIME واقعی attachment بررسی، سپس رابطه `_thumbnail_id` با API metadata ذخیره و با خواندن دوباره تأیید می‌شود؛ false ناشی از «مقدار از قبل برابر است» شکست تلقی نمی‌شود. این مسیر در حضور فیلتر واقعیِ خالی‌کننده HTML آزموده شد.
2. `wp_tempnam` اکنون داخل uploads مقصد اجرا می‌شود، نه پوشه موقت سیستم. fixture با `WP_TEMP_DIR` ناموجود، درون‌ریزی کامل را گذراند؛ این کار الزام نوشتنی بودن uploads یا فضای دیسک را حذف نمی‌کند.
3. خطای اصلی WP_Error، کد خطا و نام دارایی حفظ می‌شوند؛ برای هر فایل خطادار یک پیام، نه یک پیام تکراری برای هر یک از ۷۱ مقاله. خطای directory/copy/temp، MIME، اتصال metadata و استثنای افزونه ثالث از هم قابل تشخیص‌اند. خطا فقط در جریان اجرای مدیریتی نمایش داده می‌شود؛ لاگ دائمی یا ارسال بیرونی اضافه نشده است.

## سازگاری واقعی قالب و موتور WebP

`Demo_Media` تنها مسیر مشترک تصاویر دمو است: کپی موقت امن، `media_handle_sideload`، هوک موجود `wp_handle_upload` و همان `WebP_Uploads`، سپس metadata و subsizes رسمی وردپرس. MIME ثابت JPEG حدس زده نمی‌شود؛ URL و شناسه نهایی attachment در تنظیمات المنتور/HTML دمو ذخیره می‌شوند. از query/hash محتوا و سیاست تبدیل برای استفاده مجدد استفاده می‌شود. تغییر کیفیت/محدودیت/فعال بودن موتور یا قابلیت WebP سرور، cache policy را عوض می‌کند؛ رسانه قدیمی که ممکن است در محتوای مشتری استفاده شده باشد حذف نمی‌شود. بنابراین اجرای متوالی با سیاست یکسان تکراری نمی‌سازد، ولی تغییر آگاهانه سیاست می‌تواند نسخه رسانه تازه ایجاد کند؛ قفل توزیع‌شده برای دو import هم‌زمان ادعا نمی‌شود.

تمام **۱۶ فایل raster همراه قالب**، شامل چهار کاور، لوگوهای PNG، avatar و تصاویر دیگر، در آزمون واقعی به این مسیر داده شدند. در آن آزمون با WebP مجاز و `only_smaller=false`، همه خروجی‌ها دارای bytes و MIME واقعی WebP بودند؛ اصل فایل داخل قالب دست‌نخورده ماند. در تنظیم پیش‌فرض، خروجی بزرگ‌تر جایگزین نمی‌شود؛ موتور خاموش/codec ناموجود/MIME غیرمجاز نیز می‌تواند JPEG/PNG سالم را حفظ کند. این «سازگاری کامل مسیرهای رسانه» است، نه وعده تبدیل فنی ناممکن هر فرمت یا تأیید همه میزبان‌ها.

درون‌ریزی کامل، گزینه‌های انتخاب‌شده WebP و Lazy کاربر را بازنشانی نمی‌کند. SVG و فونت/آیکن برداری وارد تبدیل raster نمی‌شوند. screenshot صفحه انتخاب دمو دارایی مدیریتی است، نه تصویر نمایشی سایت.

### سایت دارای دمو

پس از نصب **هر دو ZIP قالب و companion rc.5** و پشتیبان‌گیری:

- «مقالات و تصاویر شاخص»: تکمیل/ترمیم ۷۱ مقاله، بدون بازنشانی برگه‌ها و تنظیمات قالب.
- «ترمیم تصاویر دمو»: اصلاح فقط نشانی و شناسه تصاویر در رکوردهای نشان‌دار دمو، attachmentهای شناخته‌شده قدیمی و thumbnailها، بدون بازسازی چیدمان المنتوری یا تنظیمات. رکورد مشتریِ فاقد نشان دمو تغییر نمی‌کند. تصویر معتبر مشتری حفظ می‌شود. CSS cache همان رکورد در صورت تغییر داده تصویر باطل می‌شود.
- برای نصب تازه، «دموی کامل» کافی است؛ تنظیمات نمایشی دمو طبق انتخاب کاربر وارد می‌شوند.

چیدمان قبلی، بنر، کارت‌ها، دو ستون، رنگ‌بندی و فرم رادیویی حفظ شده‌اند؛ فقط گزینه ترمیم تصاویر و رنگ/role صحیح پیام خطا اضافه شده‌اند. بازطراحی صفحه انجام نشده است.

### OCDI و بسته WXR

چهار attachment شبکه‌ای WXR قدیمی به `raw.githubusercontent.com/main` متکی بودند و مسیر مستقل دانلود importer می‌توانست موتور استاندارد را دور بزند. این رکوردها و `_thumbnail_id`های خارجی از **سورس فعال WXR** حذف شدند. تصاویر بعد از import توسط companion از فایل‌های همراه قالب ثبت می‌شوند. placeholderهای تصاویر در generator قابل بازتولیدند و `portable-demo-export.py` دیگر آرشیوهای تاریخی را بازنویسی نمی‌کند. native importer به شبکه نیاز ندارد. callback پس از OCDI از همان مسیر استفاده می‌کند؛ UI/AJAX/parser خود افزونه OCDI در این چرخه اجرا نشده است.

## Lazy load

مسئول اجرا companion است؛ گزینه «بارگذاری تنبل تصاویر» در بخش «بهینه‌سازی تصاویر» قالب به‌طور پیش‌فرض روشن است و Site Health وضعیت آن را نشان می‌دهد.

- HTML تصاویر attachment، محتوای نوشته، ابزارک و خروجی ویجت Elementor، و خروجی نهایی HTML قالب (از جمله هدر/فوتر و `<picture><img>`) از API رسمی `WP_HTML_Tag_Processor` عبور می‌کند. `loading=lazy` و در صورت نبود مقدار، `decoding=async` افزوده می‌شود.
- `src`، `srcset`، `sizes`، ابعاد، alt و sourceهای picture حذف/تعویض نمی‌شوند؛ placeholder و JavaScript اجرایی تازه لازم نیست و نسبت تصویر حفظ می‌شود.
- `fetchpriority=high`، `loading=eager`، `data-zc-eager`، `custom-logo`، `skip-lazy` و `no-lazy` برای جلوگیری از آسیب LCP مستثنا هستند. لوگوی هدر صریحاً eager است؛ تصویر اصلی مقاله هم از قبل eager/high بود. تأخیر دادن این تصاویر برای «همه lazy» می‌تواند هدف سرعت اولیه کاربر را خراب کند.
- خروجی admin/REST/AJAX/feed/XML/JSON/download و پیش‌نمایش Elementor/Customizer بافر نمی‌شود. تبدیل HTML تکرارپذیر/idempotent است. خروجی فشرده یا غیر HTML دستکاری نمی‌شود؛ برای محافظت حافظه، تبدیل HTML بیش از ۴ MiB انجام نمی‌شود (فیلتر attachment همچنان برقرار است).
- مرورگر زمان دقیق درخواست lazy را تعیین می‌کند. این قابلیت برای عناصر IMG است؛ پس‌زمینه CSS، canvas، تصویر داخل iframe خارجی یا تصویر ایجادشده مستقل توسط اسکریپت ثالث را نمی‌توان با attribute بومی IMG کنترل کرد. مدل‌های raster فعلی دمو از IMG استفاده می‌کنند؛ Lazy background دلخواه افزونه‌های ثالث ادعا نشده است. امتیاز یا درصد افزایش سرعت تضمین نشده است.

| widget / release guards / demo package | ۶ / ۶ / ۴ تست |

محیط یکپارچه WordPress 6.8.3، PHP 8.5.10 تحت WASM، GD و SQLite drop-in رسمی `d2082798c7371934a3565d692bf7aeb6a20376da` بود؛ HTTP و ایمیل fixture مسدود بودند. مرورگر با `playwright-core` و Chromium 133 بسته `@sparticuz/chromium` اجرا شد؛ libهای NSS همراه همان بسته فقط در محیط موقت استخراج شدند. آزمون مرورگر، fixture HTML تولیدشده توسط کلاس واقعی PHP را مصرف کرد، نه پیاده‌سازی جایگزین.

این اعداد، تأیید سایت زنده کاربر، MySQL، Imagick، همه نسخه‌های Elementor/WooCommerce/offload، همه تنظیمات قدیمی، امتیاز PageSpeed/GTmetrix یا تأیید تجاری نیستند. محدودیت‌های پیشین gateها حفظ شده‌اند. موجودی ایستای پنل: ۱۶۳ کنترل در ۱۹ بخش؛ مرجع متنی اثبات عملکرد همه کنترل‌ها نیست.
